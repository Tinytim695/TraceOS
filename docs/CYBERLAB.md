# TraceOS CyberLab

Status: **foundation implementation in progress**
Scope: dual-mode laboratory for TraceOS Live USB and installed deployments.

## Goals

CyberLab is the isolated virtual laboratory paired with TraceOS Exposure Intelligence. Exposure Intelligence discovers and prioritises weaknesses on approved assets; CyberLab reproduces selected behaviours against disposable, intentionally vulnerable lab targets.

The same scenario format, evidence metadata, isolation policy and Control Centre interface must work in both operating modes.

## Operating modes

### Live USB / portable mode

- Detect the live session and report its resource envelope.
- Use a user-selected external SSD for persistent VM images and experiment evidence.
- Do not assume the live overlay or home directory is persistent.
- Prefer one small guest at a time; cap memory and storage per experiment.
- Make disposable sessions the default.
- Never automatically partition, format, encrypt or mount a storage device.

### Installed / full mode

- Use an explicitly configured CyberLab storage root.
- Support multiple VMs and private internal lab segments when the backend is implemented.
- Keep golden images, disposable overlays, snapshots and evidence in separate areas.
- Apply resource budgets before starting any VM.
- Provide snapshot rollback and clean shutdown as first-class operations.

Hardware tier labels are guidance only. CPU architecture, RAM, disk capacity, storage speed, QEMU presence and KVM access all affect practical capacity.

## Isolation policy

The launch policy is deny-by-default.

Prohibited in all modes:

- External uplinks, NAT and bridged networking.
- Host port forwarding.
- Shared host folders.
- Host/guest clipboard sharing.
- USB and arbitrary host-device passthrough.
- Launch without a clean pre-experiment rollback snapshot.

A future multi-VM private network must be created and owned by CyberLab itself. Its identifier must be generated by the CyberLab backend, not supplied as an arbitrary host bridge. It must have no route, NAT, DNS forwarder, port forward or other path to the host LAN or internet.

The only QEMU network option currently approved by the foundation is -nic none. The private internal network mode is a policy/schema reservation only; it is not yet backed by a runtime network creator. No UI action may claim a guest is isolated merely because a checkbox is selected.

For high-risk malware analysis, use a dedicated physically disconnected host. Virtual-machine isolation is defence-in-depth, not an absolute guarantee against hypervisor escape.

## Evidence and storage

Keep separate roots for:

1. Verified golden images (read-only to experiments).
2. Disposable guest overlays and snapshots.
3. Experiment output and evidence.

Evidence records should capture scenario ID/version, target image digest, VM configuration digest, isolation assessment, operator intent, timestamps, tool versions, event logs and final snapshot/hash references.

Do not place malware samples or guest-controlled files directly in the host evidence directory. Future import/export must use a narrow, audited transfer path with size limits, content hashing and explicit operator approval.

## Current foundation implementation

The first code slice provides:

- Read-only host detection for architecture, CPU count, memory, storage, live/installed mode, QEMU and KVM.
- Conservative hardware tier estimates.
- A declarative isolation policy validator.
- A safe -nic none QEMU argument helper.
- A Control Centre CyberLab status page.
- Unit tests for resource parsing, isolation policy and UI registration.

It does **not** create or start VMs, configure virtual networks, install QEMU, run proof-of-concept code, import malware or perform active network operations.

## Delivery sequence

1. Host capability detection and read-only Control Centre page.
2. Storage-root selection and safe permissions.
3. QEMU backend with no-network single-VM launch.
4. Disposable overlays, snapshots and rollback.
5. Private internal-only network backend, with host route/NAT/bridge escape tests.
6. Curated vulnerable target images and scenario manifests.
7. Controlled PoC execution and blue-team telemetry.
8. Malware-analysis workflow on a separate, strongly isolated profile.
9. Exposure Intelligence and case/evidence integration.
10. QEMU integration tests and physical hardware validation for Live USB and installed modes.

## Release gates

Do not call CyberLab ready until automated tests demonstrate:

- No VM is started by the Control Centre during boot or page rendering.
- Network-free VM configuration contains no virtual NIC.
- Private network traffic remains inside the CyberLab virtual switch.
- No forwarding, NAT, bridge or external route exists.
- No shared folders, clipboard or USB passthrough is configured.
- A clean snapshot is required and rollback is verified.
- Host storage and networking remain unchanged after a lab run.
- Failed isolation checks block launch and are recorded.
